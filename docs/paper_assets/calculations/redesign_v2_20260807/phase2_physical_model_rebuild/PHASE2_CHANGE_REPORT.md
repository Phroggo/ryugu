doesn't drift back to a guess on the next regeneration.

## 2. What changed in each file

### `scripts/generate_detailed_spacehopper.py`
- New `hollow_cyl_inertia(m, r_outer, r_inner, l)` helper (annulus/tube
  inertia about its own center) — replaces `cyl_inertia` (solid) at every
  call site that's actually a hollow real part.
- `inertia_block()` extended with optional `ixy`/`ixz`/`iyz` and
  `com_pose` parameters (CoM offset from the link origin), defaulting to
  the old behavior (zero off-diagonals, no offset) everywhere except
  `base_link`. Every pre-existing call site is unaffected.
- `RW_RADIUS` 0.06→0.05m, new `RW_BORE_RADIUS`=0.042m, `RW_LENGTH`
  0.02→0.01m, new `RW_MASS`=0.185kg. Applied to all 3 `rw_x/y/z` links
  (inertia *and* visual geometry, so the visual now matches the physics).
- `THIGH_RADIUS` unchanged (0.015m), new `THIGH_BORE_RADIUS`=0.014m, new
  `THIGH_MASS`=0.0219kg. Same treatment for `CALF_*` (bore=0.009m,
  mass=0.0143kg). Visual geometry (outer radius) unchanged — only the
  inertial block changed for legs, since the tube wall is an internal
  detail with no visible effect on the existing outer-radius visual.
- New `SOLAR_MASS`=0.0152kg constant, applied to the solar panel's
  `box_inertia` call (was hardcoded 0.15).
- New `BASE_LINK_MASS`/`BASE_LINK_COM`/`BASE_LINK_I{XX,YY,ZZ,XY,XZ,YZ}`
  constants (1.3689kg, CoM offset, full tensor — see §4), replacing the
  old `box_inertia(1.35, CHASSIS_SIZE, CHASSIS_SIZE, CHASSIS_SIZE)` call
  with a direct `inertia_block(...)` call using these values plus the new
  `com_pose` parameter.
- Every change carries an inline comment dated 2026-08-07 explaining what
  changed and pointing at `AUDIT_TABLE.md`/this phase's folder.

### `models/spacehopper/model.sdf`
Regenerated by running the updated generator script (not hand-edited).
`git diff` confirms the change is **numbers-only plus the RW visual
radius/length** (an intentional, expected consequence of fixing the RW
geometry — the visual now matches the real annulus's outer envelope) — no
joints, links, or plugins added/removed/reordered; every pose, joint axis,
damping value, and visual mesh outside of `base_link`/`rw_*`/leg/solar
`<inertial>` blocks is byte-identical to before.

### `compute_new_inertial_model.py` (new)
Computes `base_link`'s new lumped mass/CoM/full-tensor by summing every
Phase-1-audited component that has no link of its own (chassis structure,
RW motors, leg motor+gearhead assemblies, avionics, power, antenna,
cameras, MLI) at real physical positions, via the parallel-axis theorem —
same method as `compute_moi.py`'s platform-level I_bot, generalized from a
single (zz) axis to the full 3×3 tensor plus a CoM offset. The chassis
structure's own sub-assembly (6 CFRP panels + 12 aluminum edges) is
computed the same way, nested one level in. Every position not taken
directly from an existing `model.sdf`/generator visual pose (thigh/calf
hip-joint locations, the battery grid centroid, antenna mast position,
camera positions) is flagged as an explicit assumption in the script's own
comments.

### `compute_whole_robot_cg_inertia.py` (new)
Extends `compute_moi.py`'s existing parallel-axis method (unchanged
postures, unchanged frame-resolution logic) to report the full 3×3 tensor
and the whole-body CoM (not just I_zz), and adds support for reading a
link's `<inertial><pose>` CoM offset — needed because `base_link` now has
one and the original script assumed every link's inertial frame was
coincident with its link origin. Run against both the old and new
`model.sdf` for a direct, reproducible comparison (§4).

### `CG_INERTIA_REPORT.md` (new) — the checkpoint deliverable
Full old-vs-new table: total mass, CG (x,y,z) relative to `base_link`'s
own origin (not a magnitude, not a summary statement), and the full
inertia tensor, for all 3 postures `compute_moi.py` already uses. See §4
for the numbers.

## 5. Anything that didn't go as planned

- **The whole-body CG/inertia runtime smoke test hit the same silent
  shell-abort issue documented in earlier phases** (a bare `pkill` with
  nothing to match returns exit 1, and this environment's shell aborts the
  rest of the script with zero output when that happens). First attempt
  (inline multi-line command) failed silently exactly as before; resolved
  the same way — routed through a standalone script file
  (`run_smoketest.sh`, not checked in, scratch-only) rather than an inline
  command. Noting this again since it's now hit 3+ times across phases —
  worth fixing at the shell/tooling level rather than working around it
  every time.
- **Physical placement of lumped sub-components required real engineering
  judgment calls**, not just arithmetic. Where an existing visual pose
  already established a real position (leg hip-joint locations, the
  battery cell grid centroid, antenna mast, camera bodies), that was
  reused rather than inventing a new one. Where nothing existed (RW motor
  position relative to its flywheel, avionics stack location, MLI
  distribution, knee-motor position), a stated, flagged assumption was
  made — documented in `compute_new_inertial_model.py`'s own comments, not
  buried. These assumptions affect the CG offset and off-diagonal inertia
  terms specifically; a future phase with real CAD data should treat this
  phase's placements as provisional.
- **New finding, not previously flagged:** `generate_detailed_spacehopper.py`'s
  `battery_visuals()` docstring says "12 Ni-MH cell visuals" and
  `swarm_manager.py`'s existing comments also reference "Ni-MH Battery
  Simulation" — but Table I and Phase 1's audit both say "4× Li-ion
  18650 cells" (and Phase 1 sourced a Li-ion part, the Panasonic
  NCR18650B). Chemistry *and* count disagree across three places in this
  project (visual model: 12× Ni-MH; swarm_manager.py comments: Ni-MH;
  paper Table I / Phase 1 audit: 4× Li-ion). Not resolved here — Phase 2
  placed the Phase-1-audited mass (4-cell Li-ion figure) at the visual
  grid's spatial centroid regardless of the count/chemistry mismatch,
  since repositioning mass doesn't require resolving what's actually
  inside the pack. Flagged for whoever reconciles Table I next.
- **New finding, not previously flagged:** the antenna visual
  (`antenna_mast()`) models *both* a UHF whip antenna *and* a separate
  S-Band patch antenna ("per Research_Paper.md §4.2"), which may actually
  reconcile Phase 1's flagged "Table I says S-Band, sourced part is UHF"
  mismatch — this could be a genuine two-antenna system rather than a
  contradiction. Not resolved here (Phase 1's audited antenna mass, ≈15g,
  covers only the whip mast that Phase 2 placed a position for); if it's
  really two antennas, the S-Band patch needs its own mass line before
  Table I is rebuilt.
- **New finding, not previously flagged:** the visual model has a 4th
  camera (`sci_camera`, downward-facing, at (0,−0.04,−0.105)) that Phase
  1's audit didn't count (3 cameras costed: navcam + 2 hazcams). Not added
  to `base_link`'s mass here, to stay faithful to what was actually
  costed in Phase 1 rather than silently expanding scope mid-phase —
  flagged for Phase 1's audit to be revisited/re-run if this is a real
  4th camera.
- **The platform-level I_bot figure the paper currently cites (§3.2/§7.1,
  "0.016–0.019 kg·m²," backed by `I_bot_derivation.md`/`compute_moi.py`)
  is now stale** — this phase's own whole-robot I_zz figures (§4 above)
  are 35–40% lower. Not updated in the paper text this phase (that's
  downstream documentation work); flagged in `CG_INERTIA_REPORT.md` and
  here so it isn't missed.

## 6. Checkpoint verdict

**Checkpoint (from the phase instructions): "total mass, full (x, y, z)
CG location, and full inertia tensor for the new model, reported alongside
the old (lumped, 1.35kg-base_link) values for direct comparison. Confirm
total mass is still 2.50kg, or report the new true total if it's
changed."**

**PASS.** All three required figures are reported in `CG_INERTIA_REPORT.md`
alongside their old-model counterparts, computed by the same script against
both `model.sdf` versions (not hand-transcribed from two different runs).
Total mass changed to 2.2977 kg — reported as the new true, reconciled
figure rather than forced back to 2.50 kg, per the checkpoint's own explicit
allowance. CG is reported as full (x, y, z), not a magnitude or a
"stayed near centroid" summary — and it did *not* stay near the old
centroid in z, which is exactly the kind of thing this checkpoint exists to
catch before Phase 3's pivot-torque calculation inherits a wrong number.

Regenerated `model.sdf` passed both static SDF validation and a live
runtime smoke test (spawns, free-falls under Ryugu gravity with a sane
velocity, no NaN/instability) — not a full behavioral re-verification of
righting/launch/landing (that's explicitly later-phase work), but confirms
the new physical model is at least loadable and stable, not just
numerically self-consistent on paper.
